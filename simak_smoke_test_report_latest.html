Alur Pelaksanaan Uji Coba (Smoke Test)

Proses pengujian otomatis dilakukan melalui simulasi request HTTP (curl) menirukan user agent nyata dari sisi kontraktor publik dan admin sistem.

1
Setup & Autentikasi Admin
Program melakukan POST request ke /masuk untuk mendapatkan cookie sesi admin yang valid di remote server. Sesi ini disimpan di dalam jar cookie lokal.
2
Saringan Baris Tersembunyi (Hidden Row Resolution)
Melakukan parsing pohon relasi database master template untuk menyaring baris-baris checklist. Baris di bawah parent yang memiliki status is_hidden_share = 1 (seperti menu persiapan pengadaan) dikeluarkan agar tidak menyebabkan kegagalan upload pada link share publik.
3
Pembuatan Kontrak Baru
Membuat 3 kontrak baru per modul. Program mengirim payload form kontrak ke API dashboard admin, lalu mengambil ID kontrak yang dihasilkan.
4
Pembuatan & Validasi Share Link
Admin meminta pembuatan tautan share publik (valid selama 1 minggu). Kode token share link 48-karakter dihasilkan dan disimpan di database.
5
Simulasi Publik & Upload Dokumen
Menggunakan token share untuk mengakses halaman share dengan bypass OTP. Dokumen draf/final diupload menggunakan metode terpilih (file local, Google Drive, atau penanda tidak ada). Program memvalidasi constraint pencegah upload final jika draf belum sesuai.
6
Simulasi Verifikasi KI Admin
Admin melakukan verifikasi kelengkapan dan status kesesuaian berkas checklist. Status disimpan sebagai "Sesuai" atau "Tidak Sesuai".
7
Audit Metrik Kepatuhan
Database menghitung ulang rasio kelengkapan berkas kontrak (persentase target kelengkapan > 20% dan tidak sesuai > 5%) dari total leaf rows aktif.

Poin Kriteria Uji Coba Terperinci (Smoke Test Rules)

Laporan ini memverifikasi serangkaian kriteria dan batasan logika untuk menjamin tidak ada celah keamanan atau anomali status data:

1. Logika Pembatasan Dokumen (Constraints)

  • Draft Blocking: Dokumen final mutlak dilarang dikirim jika draf-nya belum diverifikasi Sesuai oleh admin. Uji coba memvalidasi bahwa endpoint upload final memblokir dan mengembalikan feedback error jika draf masih status pending.
  • Status Ganda: Admin tidak diizinkan mengubah verifikasi final menjadi Sesuai jika file draf sebelumnya dinilai "Tidak Sesuai" (ditolak).

2. Pengujian Tipe Upload Dokumen

  • Metode File: Mengirim berkas nyata bertipe PDF (untuk dokumen final) dan XLSX (untuk draf) untuk menguji keabsahan penanganan file upload multipart di backend.
  • Metode Google Drive Link: Menguji string tautan Google Drive. Regex di controller memastikan link wajib berasal dari domain drive.google.com atau docs.google.com.
  • Metode Dokumen Tidak Ada: Memverifikasi opsi "Dokumen memang tidak ada" dengan mengisi keterangan alasan (misal: "Dokumen belum diterbitkan"). Backend mengonversi kelengkapan menjadi tidak.

3. Verifikasi Logika Hierarki Template

  • Resolusi Leaf Rows: Kepatuhan dihitung hanya berdasarkan baris terendah yang memiliki pertanyaan (leaf rows), bukan baris header kelompok.
  • Penanganan Hidden Share: Baris yang berada di bawah section dengan is_hidden_share = 1 diabaikan dari share publik agar tidak membingungkan pengguna umum, namun tetap masuk hitungan total denominator kepatuhan.

4. Pengujian Skala Besar (Volume)

  • Metrik Lengkap > 20%: Melakukan upload 31 berkas final terpisah untuk Konstruksi dan 16 berkas untuk Konsultasi, diikuti verifikasi admin "Sesuai" untuk memastikan grafik progress melompat di atas batas 20%.
  • Metrik Belum Sesuai > 5%: Mengupload 7 berkas tambahan untuk Konstruksi dan 4 berkas untuk Konsultasi dengan verifikasi admin "Tidak Sesuai" (Belum Sesuai) untuk memicu kenaikan persentase kepatuhan tidak sesuai di atas 5%.
